# Lab 1 提示词汇总（prompt.md）

本文件汇总本次实验中实际使用的全部提示词，按任务阶段组织；文末附「可直接复用的提示词模板」，供后续实验参考。

工具环境：WorkBuddy（本机路径 `E:\workbuddy\软件工程`），被分析的源码位于 WSL 的 `/home/lenovo/lab/lab1`。

## 一、源码理解阶段

### P1 初识代码库

```
@"D:/Linux_and_wsl/lab1.zip" 请先简述这份代码是什么
```

**设计意图**：初次接触陌生代码库时，先索取全局画像（是什么项目、目录结构、缺什么），再决定深入路径。带 `@文件` 附件比口头描述更精确。

---

### P2 关键指令逐条分析（练习 1 核心）

```
阅读 kern/init/entry.S内容代码，结合操作系统内核启动流程，
说明指令 la sp, bootstacktop 完成了什么操作，目的是什么？
tail kern_init 完成了什么操作，目的是什么？
```

**设计意图**：把「要解释的符号」和「解释的视角」同时给出。若只问"`la sp, bootstacktop` 是什么"，回答会退化成指令手册式的泛泛而谈；加上"结合操作系统内核启动流程"，才能得到"为何此时必须这么做"的设计动机分析。

**关键收获**：伪指令与真实指令的关系（`la` → `auipc`+`addi`）、`tail` 与 `call` 对 `ra` 的不同处理、`noreturn` 属性与指令选择的语义对齐。

**设计意图**：这类短询问看似琐碎，但把真实报错原样粘贴（而非转述）能显著加快定位效率。`cd ~//home/lenovo/lab` 的失败直接暴露了对 `~` 语义的误解，比任何解释都直观地解决了路径问题。

## 六、AI 协作经验小结

1. **附上真实文件优于口头描述**：`@文件` 或原样粘贴报错，能让 AI 基于证据而非猜测作答。
2. **给视角，不只给对象**：同一个符号，问"是什么"与问"结合 XX 流程说明为何这样设计"，答案质量差距很大。
3. **主动设边界**：实验有时不必追求完整实现，明确告诉 AI "跑到 XX 即可"能省下大量无关输出。
4. **AI 的推断必须自己验证**：本实验中 AI 因沙箱限制无法运行 WSL，所有 GDB 观察结果（如 `pc = 0x1000` 的实际指令）均需执行命令亲自核对后才写入报告。
5. **要求留空而非填空**：涉及人名、学号等不掌握的信息，明确要求"留白"，避免 AI 用占位符伪装成真实信息。

## 提示词 4 · 排障"banner 正常但内核无输出"

```
[PROMPT]
make qemu 只输出 OpenSBI banner，没有 (THU.CST) os is loading ...，请定位根因。
现象：banner 完整；make debug 下 b *0x80200000 断点不命中；Ctrl+C 后 pc = 0x80000428；
x/4i $pc 为 OpenSBI trap 入口指令。

[RELY]
- 环境：QEMU 8.2.2 / OpenSBI v1.3；源码未修改
- 产物已验证：hexdump 解码 bin/ucore.img 与 entry.S 源码逐条一致
- 队友同代码在 QEMU 4.1.1 / OpenSBI v0.4 环境一次跑通

[SPECIFICATION]
- 先给出可判定的假设（含验证方法），再动手
- 严格区分"现象"与"根因"，禁止猜测性修复
- 给出最小验证实验

[FAILURE]
- 未验证即改源码
- 把现象当根因（如不验证就改 sbi.c 适配所谓"新固件行为"）
```

